# 📦 Item Library Configuration (items.yml)

`items.yml` is located at `config/itemlab/items.yml`. All items must be placed under the top-level `items:` node. Run `/mtkv config reload` after making changes.

## Basic Structure

```yaml
items:
  Planks:
    material: PLAYER_HEAD
    display-name: "§f§lConstruction Lumber"
    quality: "§f§lCommon"
    category: material
    lore:
      - "§5§oDiscarded lumber left over from building the prison,"
      - "§5§oThe recycling station will pay a good price for it"
    head-texture-url: "http://textures.minecraft.net/texture/f9395389fed1a8ab1c52417e7a9b345e2d51ff068848087a00bdfdff96364acf"
    amount: 1
    max-stack-size: 1
```

- `Planks`: internal Itemlab ID. IDs are case-insensitive; do not configure duplicate IDs that differ only by case.
- `material`: vanilla Bukkit `Material`, such as `BOOK`, `DIAMOND`, or `PLAYER_HEAD`.
- `display-name`: displayed name; `§` color codes may be used.
- `quality`: quality text, added to the item Lore.
- `category`: item library category. Available values are `supply`, `valuable`, `armament`, `material`, and `keycard`. It is synchronized to Excel during import; actual trading permission is determined by the category in Excel's “Item Prices”.
- `lore`: detailed description list.
- `head-texture-url`: Mojang skin texture URL used when `material: PLAYER_HEAD`.
- `custom-model-data`: optional; used for resource-pack item appearances.
- `amount`: number of items created each time from this template, ranging from `1–64`; for example, `amount: 16` means one template entry creates 16 items.
- `max-stack-size`: maximum stacking capacity of a single item stack; this does not mean the same thing as `amount`.

## Mods and Complex Items

For hybrid-server Mod items that only need to be created by registry name, use `namespaced-id`:

```yaml
items:
  MyModIngot:
    namespaced-id: "examplemod:my_ingot"
    display-name: "§bMod Metal Ingot"
    category: material
    amount: 1
```

`material: "examplemod:my_ingot"` can also be used as shorthand. The registry name must include a namespace, and the item must be registered on the current server.

For complex items with NBT, PDC, durability, enchantments, or Mod component data, it is recommended to import them directly as `serialized-item`. Hold the original item in your main hand and run:

```text
/mtkv get itemlab import <ItemlabID> <category> [amount]
```

For example:

```text
/mtkv get itemlab import ThermalBattery material 8
```

The import amount defaults to the amount of the item in your main hand and can be set to `1–64`. The command atomically writes `serialized-item`, reloads the item library, and attempts to synchronize `trader-prices.xlsx`; importing the same ID updates the existing template. If the item cannot be rebuilt after serialization, the import fails and restores the previous configuration.

Manually editing internal `serialized-item` fields is not recommended; this structure is generated by Bukkit/the hybrid server and may differ by version.

## Trader Excel Integration

Item IDs in `trader-prices.xlsx` may use the raw Itemlab ID (such as `ThermalBattery`) or explicitly use `itemlab:ThermalBattery`. For Mod items, the explicit prefix is recommended to distinguish them from weapon system IDs.

If an item appears in Excel but cannot be traded, check the following in order:

1. Whether `items.yml` has a top-level `items:` node.
2. Whether, after removing the optional `itemlab:` prefix, the Itemlab ID matches case-insensitively and has no duplicate IDs that differ only by case.
3. Whether the Mod item can be created through `namespaced-id`, or whether `serialized-item` has been generated using the import command.
4. Whether the category in Excel column C is valid and the corresponding trader has that category enabled. The import command automatically synchronizes the name and category; trade checks use Excel as the source of truth.
5. Run `/mtkv config validate`, then run `/mtkv config reload`.
